# 1.4.4 — the deletion confirmation stops carrying a token

Issue [#417](https://github.com/atomchung/long-run-hybrid-coach/issues/417).
Priority: Current. One athlete asked to delete their account on ChatGPT, confirmed
the preview, pressed Allow once — and the apply was blocked twice by the client's own
pre-dispatch safety check before it ever reached this gateway. The same commit deletes
normally over direct MCP.

## Before → after, in user terms

| | 1.4.3 | 1.4.4 |
| --- | --- | --- |
| What the athlete does to delete | preview, one confirmation, apply | unchanged |
| What the model sends back to confirm it | the signed proposal, 483 characters of `base64.base64`, verbatim | that preview's `proposal_hash`, 64 hex characters |
| What the prepare result shows in the client's tool panel | a token-shaped string beside the preview | a hash and an expiry |
| Where the signed proposal lives | issued here, carried through the conversation, sent back over the wire | only here, for the 15 minutes it is good for |
| A gateway restart between the preview and the confirmation | the confirmation still applied | one re-preview |
| Additional page, approval or confirmation turn | none | still none |

The erasure itself is unchanged: same preview, same single confirmation, same refusals
when the account has moved since the athlete was shown what they were losing.

## Why

`applyOwnerDeletion` was the last apply route that asked the client to echo a signed
proposal back. That the token shape is what ChatGPT's checker reacted to is a
**hypothesis**, and this release does not claim to have fixed that client: the argument
was long, opaque and credential-shaped, which is a plausible trigger and an unproven one.
The change is justified without it. `applyWorkoutDelivery` stopped asking for its own
material in issue #355 — the gateway holds what it prepared and the client names it by
hash — and every argument this product no longer asks a model to carry verbatim is one
less thing to be truncated, re-wrapped, or refused by something in between. This is that
shape, applied to the one operation that cannot be taken back.

A hash is not a second credential. It names a preview this gateway is holding for one
athlete, and a hash nobody prepared, one prepared for someone else, one past its
`expires_at`, or one this process has forgotten resolves to nothing at all.

## What moved, and what did not

- `tool_catalogue_sha256`: `64e8d44ce75a338326fdee8fb2744b4865e68df4b88abdefceef6653f0bab0f4`
  → `1a6fa10574d066318a53110429dee132993ae26bf1c966a3d5372d581246ee42`, read back from
  this branch's own `tool_catalogue_sha256()`. A changed reviewed surface: **Scan Tools
  must be re-run against production and a new plugin version submitted** before the
  catalogue and the submission agree again (issue #182).
- `instructions_sha256`: unchanged at
  `2f371af4f45dca097654bbdc9cd83890530d255a33a9b10f10d838b2738d732d`, computed from this
  branch with the repository's own `orchestration.instructions()`. The served prompt names
  the two deletion tools and never named the argument, so it did not have to move —
  and a prompt that does not move is a client that does not have to re-read it.
- The canonical Agent Skill: unchanged, and so is its digest.
- Annotations: unchanged. `prepareOwnerDeletion` stays `readOnlyHint: true`. It now keeps
  its own proposal, which is exactly what `prepareWorkoutDelivery` already does under that
  same hint — process memory, no disk, no export, no log — and
  `docs/distribution/openai-review-conformance.md` states it rather than leaving it as a
  side effect no document admits.
- Submission packet: untouched. It records annotations and justifications, and neither
  moved.

## Rolling back

Both directions across the 1.4.3/1.4.4 boundary cost one re-preview and erase nothing:

- A preview prepared on 1.4.3 and confirmed on 1.4.4 is refused as an unknown field —
  `proposal` is not a key this route accepts any more, and it is named rather than
  ignored.
- A preview prepared on 1.4.4 and confirmed on 1.4.3 is refused for the missing
  `proposal`, which that build requires and this one does not send.
- A restart between the preview and the confirmation is now also a re-preview: the hold
  is process memory. It costs at most the 15 minutes a preview was good for anyway, and
  the refusal says so in a sentence the athlete's coach can act on.

There is no migration, no stored shape, and nothing written to disk either side of the
change.

## The access line now names the tool and the outcome

Issue #417 could not be answered from the logs. `tool=` was printed only when a request
spent Intervals calls, so a call that read this product's own store left a line
indistinguishable from any other `POST /mcp`; and a refused tool call is an HTTP `200`
carrying a JSON-RPC `isError` result, so the status code could not tell a refusal from an
erasure that went through.

Every request now prints ` tool=<name>` whenever a tool was named and ` outcome=<value>`
whenever this gateway decided how the call ended — the result's own `status` (`passed`,
`partial`), or `blocked:` and the closed-vocabulary error code the client was already
answered with:

```
POST /mcp -> 200 access=authenticated tool=applyOwnerDeletion outcome=blocked:confirmation_required
```

Never a `detail` sentence, never an owner, a token or any athlete value. The Intervals
figures are exactly as issue #260 left them, printed only when the request spent
something. `docs/ops/security-events.md` has the fields and the filter
(`railway logs --lines 1000 --filter "tool=applyOwnerDeletion"`).

## Validation

2,692 tests passed on a clean tree, with no skip; repository safety passed for 312
candidate files.

Seven regressions cover the new shape, each one a way to erase an account that must not
work: a prepare result that carries `proposal_hash` and nothing proposal-shaped in either
member of the MCP result, a hash nobody prepared, one athlete's hash sent by another, a
gateway that restarted between the two halves, the previous release's `proposal` field,
a delivery's own `proposal_hash` spent here, and a confirmation that never arrived. The
refusals that existed before are still reachable and still asserted: expired refuses,
inside the window deletes, and a preview prepared by another build refuses with the
"different build" sentence.

Two more hold the access line: an `exportOwnerData` call that spends nothing at Intervals
still naming itself and `outcome=passed`, and a deletion refused for want of a
confirmation printing `outcome=blocked:confirmation_required` — both asserting the line
carries neither the owner id nor the bearer.

## Not proven here

Whether ChatGPT now dispatches `applyOwnerDeletion` after one Allow is measured on the
real client after this rolls, not by this suite and not by this document. The block is
that client's own pre-dispatch check, which this product cannot see, cannot test against,
and does not control. If the block survives the change, the token shape was not the cause
and the finding stands on the issue rather than in this release note.
