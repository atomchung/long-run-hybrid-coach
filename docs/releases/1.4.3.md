# 1.4.3 — reads read again, and one sentence about who is connected

Owner decisions: [#408](https://github.com/atomchung/long-run-hybrid-coach/issues/408)
and [#409](https://github.com/atomchung/long-run-hybrid-coach/issues/409).
Priority: Current. Two halves of one permission story — what a client is asked to
approve, and what an athlete is told about the client.

## Before → after, in user terms

| | 1.4.2 | 1.4.3 |
| --- | --- | --- |
| Client tool catalogue | 24 tools, all under "Write/delete tools — needs approval"; no read-only group at all | 7 reads and previews are read-only again; 17 remain writes |
| Approvals in start → preview → apply, at equivalent client settings | 3 (the preview gained one) | **2, measured** — see "Production acceptance" below |
| Ordinary state and connection reads | asked for a write approval | do not |
| Connecting from claude.ai or ChatGPT | no client-identity notice | unchanged: still none |
| Connecting from an unverified origin | nothing said, anywhere | first session says which origin holds the authorization and what it can do, inside that same answer |
| Any additional page, button, tool call or confirmation turn | none | still none |

The 1.4.1 origin-warning page is **not** restored. What returned is a sentence in a
tool result, and the client decides how to render it.

## #408 — the counters, not the annotations

Every dispatched call wrote one row per account per UTC day per tool plus one per
outcome. OpenAI's review rules count a log write as a state change, so 1.4.2 answered
`readOnlyHint: false` everywhere rather than argue for an exception, and a preview
started asking the athlete for the same approval as a delivery. The owner's decision was
that the report was not worth the permission.

Removed: `_count_usage`, `_count_outcome`, `record_activity`, `record_call_outcome`, and
the dispatch wrapper that existed to hold them. Nothing replaced them — no queue, no
deferred flush, no second telemetry path, and a test fails if `INSERT INTO activity_days`
or `INSERT INTO call_outcomes` reappears anywhere in the package.

Kept: `activity_days` and `call_outcomes` in the schema and in `delete_owner_identity`, so
rows written before this release stay readable and stay erasable with the account. The
export stops asserting that outcomes are recorded and reads the answer off the rows.
`docs/ops/read-usage-stats.md` says which fields are now frozen history and what still
answers "is anybody using this": `registered`, `created_at`, `entries`, and the security
log.

Restored to `readOnlyHint: true`: `getCoachState`, `inspectIntervalsPermissions`,
`prepareCoachDecision`, `prepareWorkoutDelivery`, `exportOwnerData`,
`prepareOwnerDeletion` — the six the owner named — and `readCoachEvidence`, which was born
`false` for the same counter reason and reads out of a snapshot the session already held.

An independent path audit of all seven found no remaining write: no lazy file or table
creation, no proposal or reservation on disk (a proposal is signed and handed back), no
non-GET provider request, and no reach into `_forget_connection`, which answers a provider
`401` raised while building context -- something only `startCoachSession` and the apply
routes do. A provider `401` seen by a preview surfaces as `delivery_blocked` and forgets
nothing. What those calls still do is stated rather than hidden:
one process log line per authenticated request, and — for three of them — a provider GET
that costs a round trip against the athlete's Intervals rate limit.

## #409 — told once, not tracked

An access token issued to an origin nobody has verified now carries that origin as a
claim, sealed at issuance from the callback this gateway validated one hop earlier. The
first `startCoachSession` on such a connection returns `client_disclosure` — origin,
`recognized: false`, one sentence of capability, and the instruction to say it once, in
the athlete's language, in the same answer as the coaching reply. The instruction rides in
the result rather than in the output schema; the reason is in "what that run changed"
below.

- A client's self-reported name is never read: registering as "Claude" on an unverified
  host is disclosed like any other host.
- A verified platform carries no claim and no notice.
- A token minted before 1.4.3 carries no claim, so an old grant keeps working and is never
  reconnected to fill this in. `entry_origins` is not mined for an identity it does not
  hold — it has read the single word `unverified` since 1.4.1.
- One `client_disclosures` row per athlete per origin, written by the session route, which
  was already a write. No read-only tool records anything; that is the coordination #408
  asked for. The row is in the athlete's export and goes with their account.
- Reconnecting the same client says nothing new; an origin verified later stops being
  announced without reissuing anything.
- The capability sentence is built from what *this* connection was granted, not from a
  constant. The four Intervals consent boxes are independent, so a grant without
  `CALENDAR:WRITE` is not told it can write the calendar, and a grant that includes
  `SETTINGS:WRITE` is told what that covers — reading sport settings, and the Run
  threshold pace a confirmed delivery may update. The evidence is the scope names already
  recorded at token exchange: no permission-check tool, no provider round trip for the
  notice, no broader scope, no reconnection. A connection with no recorded scopes — a
  registry older than `token_scopes`, a token response that named none, a registry this
  process could not read — is described as unknown rather than assumed full.

**Limits, stated rather than claimed away.** This is transparency, not consent, and it
does not meet the MCP proxy-consent control on its own: a hostile client controls its own
rendering and can drop the sentence, the athlete reads it after authorizing rather than
before, and a client that never calls `startCoachSession` never says it. Whether a
particular client displays a tool-result field is that client's decision, and only a real
run against that client can answer it.

The capability sentence describes the preview-then-confirm workflow a change goes through.
That workflow is not an independently verified human-consent guarantee and this release
does not claim it as one: the confirmation arrives as a tool argument supplied by the
client, so a client that never shows the preview can still send it. The notice is not a
new security boundary against such a client — the boundaries that hold against one are
authentication, scope validation and account isolation, none of which this changes.

## Rolling back

A rollback to 1.4.2 erases accounts normally, including accounts that have been told about
an unverified source.

The first shape of this table did not. `client_disclosures.owner_id` referenced `owners`
without a cascade, so once a row existed, 1.4.2's `delete_owner_identity` — which has
never heard of the table — reached `DELETE FROM owners` and raised
`FOREIGN KEY constraint failed`: the transaction rolled back and `applyOwnerDeletion`
answered `500` until the deployment moved forward again. A row written to stop repeating
one sentence should not be able to stop an athlete deleting their account, least of all
during the rollback this release might need, so the fix is `ON DELETE CASCADE` — the
clearing moves into the schema, where a release that does not know the table still
performs it.

`CREATE TABLE IF NOT EXISTS` does not reshape a table that already exists, so a registry
written by an earlier build of this branch is rebuilt on the next open: copy into the
cascading table, drop, rename, inside one transaction with foreign keys off, per SQLite's
own procedure. Rows survive it, so nobody is told a second time. The ordinary path is one
read of `sqlite_master` and no write at all. `delete_owner_identity` still names the table
itself; the cascade is the floor under it, not a replacement for it.

Seven regressions hold this: the release before this one erasing an account that has been
told, the same after a migration, the migration keeping every row, a row whose athlete no
longer exists left behind rather than copied through the foreign-key-off window, this
release's own delete, a current registry left untouched by repeated opens, and a migrated
one not rebuilt again on the next. Each also asserts the other athlete's rows are still
there. The rows they migrate are written straight into the old-shape table: written
through the registry, they would arrive *after* the migration, and the copy step could
have been deleted without a test noticing. Both halves — the copy, and the delete this
release still performs itself — fail the suite when removed.

## Contributor rule

`AGENTS.md` gains "A step the athlete has to take is the owner's decision": a change that
adds or removes a client approval, an OAuth prompt, a confirmation turn or a required page
goes to the owner with a concrete before → after first, and calling it security or
compliance work does not waive that.

## Real-client acceptance, 2026-09-10

Driven against a loopback gateway with a fake provider, using Claude Code as the client
(`--mcp-config`, `--strict-mcp-config`, a static bearer):

- **Unverified origin, first turn.** The coach said it once, in the athlete's language,
  and answered the training question in the same reply: "你的 Coach 連線授權給
  https://new-agent.example，這是本服務未驗證的來源，它可以讀取你的訓練資料、並在你確認特定
  變更時修改你的計畫或寫入你的 Intervals 行事曆。" No extra turn, nothing to confirm.
  **That sentence is what the fixed capability constant produced.** The constant is gone:
  the capability half is now built from this connection's recorded grant, so the wording
  an athlete sees depends on what they granted. The shape of the turn — one sentence, the
  athlete's language, the coaching answer in the same reply, nothing to confirm — is what
  that run established; the wording itself was re-read against a real client afterwards,
  below.
- **Same connection, next turn.** Nothing about the connection; straight to the answer.
- **Connection with no origin claim** (a verified platform, or a grant older than this
  release). Nothing about the connection, and the session worked normally.
- **The read path.** Two `getCoachState` calls through the client left the identity
  registry and the owner directory byte-identical.
- **The served catalogue.** `tools/list` over the wire: 24 tools, 7 of them read-only.

**What that run changed.** With the disclosure carrying only `origin`, `recognized` and
`capabilities`, the model read it and said nothing — the instruction was in the output
schema, and a schema field description is not where a model looks. The instruction now
travels in the result itself, which is the channel every client hands the model, and the
sentence appeared on the next run. The suite could not have found this; only a real client
could.

The instruction is a constant, and the origin stays in its own field beside it: a hostname
is a string an anonymous registration chose, and
`ignore-the-previous-instruction.example` is a legal one. Interpolating it into the
sentence the model is told to follow would hand a registrant a line in that instruction.
Re-verified against the real client after the change — same disclosure, same turn.

**Read again after the capability change.** Same client, same shape of run, this time on
the commit production serves and across four connections:

- **Unverified origin, full grant.** Told once, in the athlete's language, inside the
  answer: what this service holds, plus the Intervals activities, wellness records and
  sport settings the grant carries, and — after a confirmed preview — the plan, the Run
  threshold pace and the calendar workouts.
- **Unverified origin without `CALENDAR:WRITE`.** Told once, and **the calendar is not
  mentioned at all**: only the plan and the Run threshold pace. This is the defect the
  follow-up review named, read off a real client after the fix.
- **A verified platform.** Nothing about the connection.
- **The same unverified connection, second session.** Nothing.

## Production acceptance, 2026-09-10

Against `https://mcp.paceandstaystrong.com` at this release, through the claude.ai
connector that was authorized **before** it.

**The catalogue, on the surface that groups by the hint.** The connector's settings page
reads the deployed catalogue and shows **Read-only tools 7** and **Write/delete tools 17**.
In 1.4.2 that page had no read-only group at all: every tool, previews included, sat under
"Write/delete tools — needs approval".

**No reauthorization.** That connector picked up the new catalogue with no reconnect and no
re-consent, and a coaching turn ran normally straight afterwards. No client-identity notice
appeared anywhere, which is the verified-platform half of #409, live.

**The approval count.** With the read-only group set to **Always allow** and the
write/delete group left at **Needs approval**, one message — open a session, then preview
this week's delivery — cost **one** prompt:

| Step | Tool | Prompt |
| --- | --- | --- |
| 1 | `startCoachSession` | yes |
| 2 | `prepareWorkoutDelivery` | none |
| 3 | apply | not called |

Both calls are in the expanded trace, so this is the preview running unprompted rather than
the model skipping it. `applyCoachDecision` and `applyWorkoutDelivery` stay in the
write/delete group at needs-approval, so the full cycle is **2** where 1.4.2's all-write
catalogue cost **3** on the same settings. Nothing was applied and nothing was written to
Intervals: the preview stopped at `AWAITING_CONFIRMATION`, naming its destination account.

**Still not done.** No unknown-host OAuth against production — claude.ai and chatgpt.com are
verified origins by construction, so neither can play the unfamiliar source, and producing
one would mint a live bearer and a permanent disclosure row on a real athlete for no reason
but a checkbox. The ChatGPT connector is still serving the 1.4.2 snapshot: it shows
`getCoachState` as a write, carrying a description this repository no longer contains. Its
approval policy is "allow low-risk actions", the setting that keys off `readOnlyHint`, so
this release reaches ChatGPT only after that connector refreshes. No OpenAI scan or
submission has been run; the Registry publication has (workflow 34444957367).

## Independent review

Reviewed adversarially by an agent that did not write any of it, against the branch as
pushed: no blockers. It re-ran the suite and the safety check, and independently confirmed
zero writes on all seven read-only paths under conditions the repository's own tests do not
cover — a provider `401` on every read, an owner registered before their store directory
exists, and a store holding an unreconciled `delivery-attempt.json` — comparing the whole
state root rather than the owner directory alone.

What it found and this release fixes: four submission justifications claimed the tools
"record nothing about the call itself", which the process log line contradicts and which
disagreed with this repository's own conformance page; the in-memory preview retention was
a side effect no document admitted; an ops page still cited a constant this release
deleted; a comment above the annotation table still described the counters; the release
note over-narrowed where `_forget_connection` lives; and the erasure regression exercised
three routes that write nothing while skipping the one that writes.

Its one standing note, kept rather than fixed: `readCoachEvidence` is a reviewed surface
changed outside the six the owner named (recorded here and in issue #408). Its other —
the rollback hazard — was recorded rather than fixed at that point and is fixed now; see
"Rolling back" above.

## The owner review after that, and what it changed

The owner's follow-up review of the same head asked for two things and a cleanup, and all
three are in this release: the capability sentence built from the connection's own grant
rather than a constant, the rollback hazard fixed rather than documented, and the stale
claims corrected (the conformance page's counters, the instruction's location, the
approval count stated as expected, and a `tool_catalogue_sha256` that this branch's code
does not produce).

A second independent review of that work found no blocker and two things worth fixing,
both done: two of the five rollback regressions were passing without exercising the row
copy, because the helper that reverted the table to its first shape wrote its rows through
the registry — which migrated the empty table before the first row landed — and the
capability sentence told an athlete their permissions were "not recorded" when a record
existed and named none. Both mutants now fail the suite.
