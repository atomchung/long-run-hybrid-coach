# 1.4.3 — reads read again, and one sentence about who is connected

Owner decisions: [#408](https://github.com/atomchung/long-run-hybrid-coach/issues/408)
and [#409](https://github.com/atomchung/long-run-hybrid-coach/issues/409).
Priority: Current. Two halves of one permission story — what a client is asked to
approve, and what an athlete is told about the client.

## Before → after, in user terms

| | 1.4.2 | 1.4.3 |
| --- | --- | --- |
| Client tool catalogue | 24 tools, all under "Write/delete tools — needs approval"; no read-only group at all | 7 reads and previews are read-only again; 17 remain writes |
| Approvals in start → preview → apply, at equivalent client settings | 3 (the preview gained one) | 2, as in 1.3 |
| Ordinary state and connection reads | asked for a write approval | do not |
| Connecting from claude.ai or ChatGPT | no client-identity notice | unchanged: still none |
| Connecting from an unverified origin | nothing said, anywhere | first session says which origin holds the authorization and what it can do, inside that same answer |
| Any additional page, button, tool call or confirmation turn | none | still none |

The 1.4.1 origin-warning page is **not** restored. What returned is a sentence in a
tool result, and the client decides how to render it.

## #408 — the counters, not the annotations

Every dispatched call wrote one row per account per UTC day per tool plus one per
outcome. OpenAI's review rules count a log write as a state change, so 1.4.2 answered
`readOnlyHint: false` everywhere rather than argue for an exception, and a preview
started asking the athlete for the same approval as a delivery. The owner's decision was
that the report was not worth the permission.

Removed: `_count_usage`, `_count_outcome`, `record_activity`, `record_call_outcome`, and
the dispatch wrapper that existed to hold them. Nothing replaced them — no queue, no
deferred flush, no second telemetry path, and a test fails if `INSERT INTO activity_days`
or `INSERT INTO call_outcomes` reappears anywhere in the package.

Kept: `activity_days` and `call_outcomes` in the schema and in `delete_owner_identity`, so
rows written before this release stay readable and stay erasable with the account. The
export stops asserting that outcomes are recorded and reads the answer off the rows.
`docs/ops/read-usage-stats.md` says which fields are now frozen history and what still
answers "is anybody using this": `registered`, `created_at`, `entries`, and the security
log.

Restored to `readOnlyHint: true`: `getCoachState`, `inspectIntervalsPermissions`,
`prepareCoachDecision`, `prepareWorkoutDelivery`, `exportOwnerData`,
`prepareOwnerDeletion` — the six the owner named — and `readCoachEvidence`, which was born
`false` for the same counter reason and reads out of a snapshot the session already held.

An independent path audit of all seven found no remaining write: no lazy file or table
creation, no proposal or reservation on disk (a proposal is signed and handed back), no
non-GET provider request, and no reach into `_forget_connection`, which answers a provider
`401` on the session route alone. What those calls still do is stated rather than hidden:
one process log line per authenticated request, and — for three of them — a provider GET
that costs a round trip against the athlete's Intervals rate limit.

## #409 — told once, not tracked

An access token issued to an origin nobody has verified now carries that origin as a
claim, sealed at issuance from the callback this gateway validated one hop earlier. The
first `startCoachSession` on such a connection returns `client_disclosure` — origin,
`recognized: false`, and one sentence of capability — and the served output schema tells
the model to say it once, in the athlete's language, in the same answer as the coaching
reply.

- A client's self-reported name is never read: registering as "Claude" on an unverified
  host is disclosed like any other host.
- A verified platform carries no claim and no notice.
- A token minted before 1.4.3 carries no claim, so an old grant keeps working and is never
  reconnected to fill this in. `entry_origins` is not mined for an identity it does not
  hold — it has read the single word `unverified` since 1.4.1.
- One `client_disclosures` row per athlete per origin, written by the session route, which
  was already a write. No read-only tool records anything; that is the coordination #408
  asked for. The row is in the athlete's export and goes with their account.
- Reconnecting the same client says nothing new; an origin verified later stops being
  announced without reissuing anything.

**Limits, stated rather than claimed away.** This is transparency, not consent, and it
does not meet the MCP proxy-consent control on its own: a hostile client controls its own
rendering and can drop the sentence, the athlete reads it after authorizing rather than
before, and a client that never calls `startCoachSession` never says it. Whether a
particular client displays a tool-result field is that client's decision, and only a real
run against that client can answer it.

## Contributor rule

`AGENTS.md` gains "A step the athlete has to take is the owner's decision": a change that
adds or removes a client approval, an OAuth prompt, a confirmation turn or a required page
goes to the owner with a concrete before → after first, and calling it security or
compliance work does not waive that.

## Validation

2,649 tests passed with one skip; repository safety passed. The seven read-only claims are
held to byte equality against the owner directory *and* the identity registry, on the
answered call, the refused one and a retry loop. Eight regressions cover the disclosure:
unverified origin told once and not again, verified platform never told, spoofed client
name disclosed anyway, pre-1.4.3 grant unaffected, read-only tool neither disclosing nor
recording, second authorization from the same source silent, an origin verified later
silent, and the notice carrying no URL, token or client id.

## Real-client acceptance, 2026-09-10

Driven against a loopback gateway with a fake provider, using Claude Code as the client
(`--mcp-config`, `--strict-mcp-config`, a static bearer):

- **Unverified origin, first turn.** The coach said it once, in the athlete's language,
  and answered the training question in the same reply: "你的 Coach 連線授權給
  https://new-agent.example，這是本服務未驗證的來源，它可以讀取你的訓練資料、並在你確認特定
  變更時修改你的計畫或寫入你的 Intervals 行事曆。" No extra turn, nothing to confirm.
- **Same connection, next turn.** Nothing about the connection; straight to the answer.
- **Connection with no origin claim** (a verified platform, or a grant older than this
  release). Nothing about the connection, and the session worked normally.
- **The read path.** Two `getCoachState` calls through the client left the identity
  registry and the owner directory byte-identical.
- **The served catalogue.** `tools/list` over the wire: 24 tools, 7 of them read-only.

**What that run changed.** With the disclosure carrying only `origin`, `recognized` and
`capabilities`, the model read it and said nothing — the instruction was in the output
schema, and a schema field description is not where a model looks. The instruction now
travels in the result itself, which is the channel every client hands the model, and the
sentence appeared on the next run. The suite could not have found this; only a real client
could.

The instruction is a constant, and the origin stays in its own field beside it: a hostname
is a string an anonymous registration chose, and
`ignore-the-previous-instruction.example` is a legal one. Interpolating it into the
sentence the model is told to follow would hand a registrant a line in that instruction.
Re-verified against the real client after the change — same disclosure, same turn.

**What that run could not show.** Claude Code's CLI asks permission for every MCP tool
regardless of `readOnlyHint`, so the approval-count change is not observable there. The
surface that groups by the hint is the claude.ai connector's own settings page, which
reads the deployed catalogue — so that half of #408's acceptance needs a production deploy
and a live connector, and has not been run.

**Not verified here:** no production deploy, no `/readyz`, no Registry publication, no
OpenAI scan or submission, and no acceptance against a real client UI. This release note
records what the code and the suite hold, and nothing about what any client shows.
