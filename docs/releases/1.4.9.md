# 1.4.9 — the product round, and two first conversations that could not happen

1.4.8 was the engineering round and changed nothing an athlete does. This one is the
opposite: no architecture moved, and two of the fixes are the difference between a
first conversation working and a first conversation failing silently.

Priority: **Current**, with two findings that were Blockers until this release.
**`tool_catalogue_sha256` and `instructions_sha256` both moved**, so this is a new
reviewed surface. `skill_sha256` did not, and the tool count is still 22 — what changed is
one tool's input-schema description and one paragraph of the served prompt, both because a
fix below is unreachable without them.

## Before → after, in user terms

| | 1.4.8 | 1.4.9 |
| --- | --- | --- |
| What an athlete does, anywhere | preview, one confirmation, apply | unchanged |
| Approvals in start → preview → apply | 2 | 2 |
| Tool count | 22 | 22 |
| Upload a year of training, then ask for a first plan | above ~130 sessions the client discarded the whole answer, with no error and no smaller read to fall back to | the last 42 days are read, the window is stated, and the answer fits |
| Report a session on a day an upload already holds one of that sport | the upload's session was overwritten and the reply called it a restatement | both stand, unless the athlete's words describe the upload's own session |
| Re-send a Garmin Connect export naming its distance unit, as the reader asks | refused as a duplicate upload; the kilometres could never be stored | accepted, merged into the sessions already on record, distances filled in |
| Arrive without one Intervals permission ticked | a reconnect prompt identical to a revoked credential, with nothing naming the box | the coach reads the refusal and can call `inspectIntervalsPermissions`, which names it |
| State first-plan availability as prose ("週一晚上") | stored as null, discovered after confirming, asked again next conversation | named at preview, in the turn that can still fix it |

## The two that were blockers

### A year of uploaded history made the first answer undeliverable

`importAthleteHistory` invites a long history "in parts, by year", and a year of running
at three sessions a week is 156 rows. `pre_plan_observations` carried every stated record
whole — the comment that stood there said "there are a handful at most before a plan
exists" — and the oversized-result guard never measured this path, because it only
measures an answer whose status is `passed` and a first conversation's is `no_plan_state`.

Measured end to end through the gateway: **85,161 characters against a 66,000 ceiling**
at 200 imported sessions. HTTP 200, no error, no `isError`. Issue #233 records what a
client does with that — it discards the result and the turn cannot happen. Every retry
was the same size, and nothing narrower was reachable: `evidence_index` and `context` are
both null before a plan exists, so `readCoachEvidence` refuses.

Issue #233 already chose windowing for the other reader of the same evidence. This applies
it to the reader it missed: the four dated families are read over the same 42 days, and
the view states `window_start`/`window_end` so an empty list cannot be read as "they have
never trained". The same account now serializes to **20,417 characters**. Long-term goals
and stated preferences stay whole — they carry no date, so there is no window to read them
over.

**The owner chose this tradeoff explicitly:** a first plan no longer sees "you ran 800 km
last year". Adding a monthly-bucket summary to recover the long view was offered and
deferred until a real first-plan transcript shows it changing the decision.

`contracts/pre-plan-observations.schema.json` gained the two fields with the payload, and
`tests/test_pre_plan_contract.py` is what caught the omission: it holds the published
document against what the gateway actually emits, in both directions. The contract is a
model-facing surface, so this release owes client acceptance — which it already owed.

### A spoken session destroyed an imported one

`_activity_summary_position` returned an imported row outright when a day held exactly one
session of that sport, bypassing the agreement check its own docstring assigns to the
caller. So an athlete who reported a 20-minute swim on a day their upload held a
*different* 40-minute swim lost the uploaded one — and because its dedup key travelled
onto the survivor, re-importing the file did not bring it back. The response called it a
restatement.

Two or more imported rows that day worked correctly. The contract was inverted in the
commonest case.

## Everything else

- **Garmin Connect distances, reachable at last.** The reader drops every distance from
  that export because it states no unit, and prints "re-send with `column_mapping` naming
  `distance_unit`". Following that literally failed three times over: a partial mapping was
  refused for having no date column, the re-send hashed to the same digest and came back
  `already_imported`, and the merge branch only appended a dedup key, so the standing
  records kept `distance_km: null` forever. A mapping on a header this module already knows
  now completes it rather than replaces it, the mapping is part of the upload's identity,
  and a merge fills a field the record holds as unknown while never overwriting a stated
  one.
- **A 403 is the athlete's consent page, not a revoked credential.** `upstream_unauthorized`
  covered both 401 and 403, so an unticked permission box was restated as a bare 401
  challenge — the athlete reconnected, ticked nothing different, and met the same blank
  challenge, with no turn in which the coach could name the box. `_forget_connection`'s own
  docstring had said "only a 401" all along. Owner decision, taken deliberately: the client's
  automatic one-click reconnect is replaced by the coach saying which permission is missing.
- **Availability prose is named at preview.** Only the seven English weekday names and the
  seven three-letter tokens parse, and the write runs after the plan is committed and
  deliberately does not unwind it — so "週一晚上" produced a warning the athlete only saw
  after confirming. The same parse now runs at preview, as a warning and not a refusal.

## What an independent review changed before this merged

The repository's own rule is that a large integration gets an adversarial reviewer who did
not write it. That review found four defects in the first cut of this release, all of them
introduced by these fixes, and one new test that did not test what it claimed:

- **The window could make the whole container vanish.** The presence check that decides
  whether to build `athlete_evidence` at all was computed from the *windowed* lists, so an
  athlete whose stated sessions were all older than 42 days — someone who imported a
  history and is restarting after a layoff — got `athlete_evidence: null`, which the
  contract reserves for an athlete who has stated nothing at all. The window was being read
  as "they have never trained": the exact misreading it was added to prevent, reached from
  the other side. Presence is now asked of everything on record; only what is emitted is
  windowed.
- **Folding the mapping into `payload_digest` moved `conflict_id`.** Question ids are built
  from that digest, and every digest already on disk was keyed by it. The mapping now
  travels beside the digest as `mapping_digest`, read only by `already_imported`.
- **A file was filling blanks in records the athlete spoke.** The merge adopted an import's
  distance and title into a standing spoken row, leaving `source: athlete_reported` and
  `imported_from: null` on numbers that came out of a file — and `source` exists so a coach
  can tell an export from somebody remembering the session. Only imported records are
  filled now, which is still the whole of the Garmin case.
- **A non-object `column_mapping` was a 500.** The recognised-header path read the caller's
  keys before validating them. A model sending the field's *name* is a plausible mistake,
  and the unrecognised-header path already answered it with the sentence that names the fix.
- **Completing a known export could silently redefine it.** `{"distance_unit": "m"}` on a
  Strava export turned 8.10 km into 8 metres, still labelled Strava. A caller key that would
  displace a column the recognised mapping already states is now refused by name.
- **One new test was theatre.** It meant to prove a stated figure is defended in a merge,
  but its second read was far enough out to become a conflict, so nothing reached the merge
  at all; the mutation it named passed. Rewritten with a re-read inside the sameness
  tolerance, and verified to fail under that mutation.

## The tooling that was supposed to catch this

- **The provider conformance probe had been dead for 28 days.** The outlook validation added
  on 2026-08-17 (#127) made its rebased fixture plan invalid, so every invocation — including
  the read-only listing — died before building a payload. It was the one script in `scripts/`
  with no test. Fixed, tested, and **run live**: all six execution shapes exact against the
  account, Intervals' own analysis present on all four targeted probes and correctly absent
  on the two open ones, probes removed afterwards and the calendar read back empty.
- **Two of the three reviewed surfaces were not pinned.** `tests/test_release_candidate_surface.py`
  wrote down the tool catalogue digest and stopped there, so the served orchestration prompt
  and the packaged Skill could move with nothing but a path rule to notice — and a path rule
  says a file changed, never that the approved bytes are no longer the served bytes. All
  three are pinned now, and the version constant with them.
- **`docs/release-inventory.md` disagreed with its own headings**, in five places at once. A
  test now reads all five numbers out of the file and holds them to each other, and holds the
  workflow-group heading to the rows in its own table.

what production serves, its bump rode inside a feature PR rather than a cut, and it had no
receipt at all.
